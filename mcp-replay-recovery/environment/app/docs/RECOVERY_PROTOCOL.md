# Recovery protocol

Each JSONL record is durable only after its complete newline has reached storage. Creating a journal also requires fsyncing its parent directory after the file itself, because a durable inode with a non-durable directory entry can disappear after power loss. A final byte sequence that is not a complete JSON record is a torn tail: recovery must preserve and process every valid record before it, truncate the incomplete bytes while holding journal ownership, and only then append new lifecycle records. Malformed data before the final non-empty record is corruption and must be rejected.

An operation is introduced by `PLANNED`. Once its dependencies and result bindings are durable, the current writer fsyncs `PREPARED` before its first authority acquisition. `PREPARED` fixes the effective dispatch key and exact resolved wire request but does not count as a dispatch attempt. `DISPATCHED` means a side-effect request may or may not have reached the tool server. `REMOTE_OBSERVED` durably records `PENDING`, `ABORTED`, or `COMMITTED` server authority discovered during reconciliation; it leaves the local lifecycle uncertain at `DISPATCHED` and does not itself count as another dispatch attempt. `RESULT_DURABLE` means the returned result is safely journaled. `ACKED` means local delivery is complete. `RESULT_RELEASED` means the server has acknowledged that the immutable result blob can be reclaimed after local durability.

A current `PREPARED` record uses this exact durable shape:

```json
{"event":"PREPARED","session_id":"session-a","operation_id":"allocate","idempotency_key":"...","request_fingerprint":"...","wire_name":"allocate_workers","wire_arguments":{"pool_id":"gpu","quantity":1,"priority":"normal"}}
```

A `REMOTE_OBSERVED` record uses this exact durable shape (with the operation's actual values):

```json
{"event":"REMOTE_OBSERVED","session_id":"session-a","operation_id":"allocate","state":"PENDING","idempotency_key":"...","request_fingerprint":"...","wire_name":"allocate_workers","wire_arguments":{"pool_id":"gpu","quantity":1,"priority":"normal"},"dispatch_token":"...","dispatch_generation":1,"remote_revision":2}
```

A newly written committed observation additionally persists its immutable result receipt:

```json
{"event":"REMOTE_OBSERVED","session_id":"session-a","operation_id":"allocate","state":"COMMITTED","idempotency_key":"...","request_fingerprint":"...","wire_name":"allocate_workers","wire_arguments":{"pool_id":"gpu","quantity":1,"priority":"normal"},"dispatch_token":"...","dispatch_generation":1,"remote_revision":3,"result_ref":"...","result_sha256":"..."}
```

After local acknowledgement, release completion uses this exact durable record:

```json
{"event":"RESULT_RELEASED","session_id":"session-a","operation_id":"allocate","result_ref":"...","result_sha256":"..."}
```

The field is named `state` and is `PENDING`, `ABORTED`, or `COMMITTED`. The key, fingerprint, `wire_name`, and `wire_arguments` become immutable at `PREPARED` and remain so for the operation lifetime. The wire fields are an inseparable pair and the fingerprint must equal `ToolClient.request_fingerprint(wire_name, wire_arguments)`. `dispatch_generation` and `remote_revision` are positive integers. The token is immutable within one generation. A successor generation is the sole documented case in which the token changes. `result_sha256` is the lowercase SHA-256 digest of the canonical compact JSON encoding of the result: object keys sorted, separators `,` and `:`, UTF-8, and non-ASCII characters unescaped. A receipt reference and digest are an inseparable immutable pair and occur only on a `COMMITTED` observation. Checkpoint entries use exactly one applicable boolean marker—`pending_observed`, `aborted_observed`, or `committed_observed`—to retain the latest durable authority observation. Revisioned records from before generation fencing omitted `dispatch_generation`, and old attempted records can omit the wire snapshot while old committed observations can omit a receipt; they remain readable as generation 1. A legacy record without a snapshot can advance only if its fingerprint is reproducible from the current migration, and its next newly written `DISPATCHED` or `REMOTE_OBSERVED` record persists the snapshot. Every other newly written attempted record includes the wire pair, generation, and revision, and every newly written committed observation includes its receipt.

The lifecycle state machine is strict across both checkpoint state and journal suffixes. `PREPARED` follows only `PLANNED`, contains the complete key/fingerprint/wire snapshot, and has zero attempts and no server token, generation, revision, authority marker, receipt, or result. A dispatch follows `PREPARED`, a legacy `PLANNED`, or another uncertain `DISPATCHED`; a remote observation follows `PREPARED`, legacy `PLANNED`, or `DISPATCHED`; a durable result follows only non-aborted `DISPATCHED`; acknowledgement follows only `RESULT_DURABLE`; and result release follows only `ACKED` with the same retained receipt. Legacy histories may contain a direct `DISPATCHED` to `RESULT_DURABLE` transition, but the current writer never emits one: every newly written durable result is preceded by a durable `COMMITTED` observation and its receipt. A legacy `ACKED` operation without a receipt remains complete; an `ACKED` operation that retains a receipt but has no `RESULT_RELEASED` record is valid pending cleanup and is released on recovery. Once `COMMITTED` authority has been observed, another dispatch or a later non-committed authority observation is corruption. Once `ABORTED` has been observed, that generation cannot become pending, committed, or be dispatched again. Only a consecutive successor generation may be dispatched, and only after the abandonment proof is durable. Discovering generation N authority from local `PLANNED` or `PREPARED` proves at least N historical attempts; an observation following `DISPATCHED` does not itself increment the existing count. Consequently, `PLANNED` and `PREPARED` have zero attempts, while every `DISPATCHED`, `RESULT_DURABLE`, `ACKED`, or `RESULT_RELEASED` checkpoint entry has at least as many attempts as its current generation. An exact duplicate `PLANNED` record is idempotent and never resets later state. Unknown events, impossible transitions, preparation after acquisition, release before acknowledgement, release receipt drift, and checkpoint entries whose attempts or retained fields contradict their status are corruption. Recovery validates the complete durable state before issuing any remote control-plane or side-effecting request.

The pair `(session_id, operation_id)` is the identity of the logical operation for its entire lifetime. Attempts, schema versions, process starts, and wire-tool names are not part of that identity. A journal may multiplex multiple sessions, and operation IDs are unique only within a session. Dependencies name operations in the same session.

Every newly written lifecycle record carries both `session_id` and `operation_id`; `PLANNED` also retains the complete nested operation. Recovery remains compatible with legacy lifecycle records that omit `session_id` when their operation ID identifies exactly one planned operation in that journal. Ambiguous legacy records are corruption.

Dependency ordering is causal, not a final-state check. At the exact journal prefix where `PREPARED`, `DISPATCHED`, or `REMOTE_OBSERVED` appears, every declared dependency must already be `RESULT_DURABLE`, `ACKED`, or `RESULT_RELEASED`. A dependency result written later cannot retroactively legalize an earlier prepared request or authority record for its child; that history is corruption and is rejected before any control-plane or side-effecting request.

Every current operation first persists `PREPARED` with the exact `idempotency_key`, semantic `request_fingerprint`, and fully resolved `wire_name` and `wire_arguments`. The fingerprint is the SHA-256 digest produced by `ToolClient.request_fingerprint` from that exact wire snapshot. `PREPARED` is fsynced before `acquire_call`, because acquisition can create durable remote authority even when its response never reaches the gateway. Retries use the prepared snapshot verbatim: they do not rerun mutable schema-migration code or resolve bindings again. This permits a request prepared under an older migration rule to reclaim or reconcile authority even when today's rule would produce different wire arguments. `DISPATCHED` and `REMOTE_OBSERVED` repeat the immutable prepared identity and add the server-issued token, positive generation, and positive remote-revision high-watermark. A successor must be exactly generation N+1, must use a different token and a higher revision, and is legal only after a durable `ABORTED` observation for generation N. The effective dispatch key is also owned by exactly one logical operation across the whole journal; key aliasing is corruption even when two operations have identical wire requests. Legacy dispatch records missing current identity or snapshot fields derive whatever is absent only when the retained fingerprint can still be reproduced, then persist a complete current-generation identity and wire snapshot before their next actual remote attempt.

The server's read-only `lookup_call` remains useful for diagnostics, but an `ABSENT` observation cannot safely authorize a side effect: an older request can become visible between lookup and dispatch. Recovery instead calls `acquire_call`, which atomically reserves an absent key and returns one of five states. Every acquisition supplies `after_revision`, the highest remote revision durably retained for that operation, and every non-conflict response carries a positive `revision`, positive `generation`, fingerprint, and token. `READY` authorizes one side-effecting request for that generation. `PENDING` means the generation may already be in flight and must be durably recorded and acquired again, never redispatched. `COMMITTED` carries an immutable `result_ref` and `result_sha256`, plus an optional inline `result` cache. The receipt is journaled before the result is trusted. This is also mandatory after an ordinary side-effect call returns successfully: the direct response is not result authority, so its payload is discarded and the generation is reacquired until authoritative `COMMITTED` state is visible. An inline authoritative result is accepted only if its canonical digest matches. If it is absent, recovery calls the read-only `read_result(result_ref, result_sha256)` tool until it returns `AVAILABLE`; `PENDING` means the result replica is not visible yet, and `CONFLICT`, receipt drift, or a digest mismatch is corruption. The available result is then recorded as `RESULT_DURABLE` and completed locally. `ABORTED` is the server's durable proof that the named generation produced no side effect and can never commit; it must be journaled before recovery can request a successor. `CONFLICT` means the key belongs to a different semantic request and is corruption: its result must not be accepted and no retry may be sent. Polling is cooperative across the currently dependency-ready operations: after a nonterminal `PENDING` acquisition, stale post-call confirmation, or `PENDING` offloaded-result read, recovery gives every other ready operation an opportunity to advance before polling that operation again. This avoids a causal deadlock when one remote state can advance only after independent business work commits.

Once `RESULT_DURABLE` and `ACKED` are both fsynced, the gateway calls `release_result(result_ref, result_sha256)` with a fresh transport request ID. `PENDING` is polled with another fresh request. `RELEASED` and `ALREADY_RELEASED` both prove the immutable receipt is tombstoned and authorize the local `RESULT_RELEASED` record; the latter is the expected answer after the server applied a release whose response was lost. `CONFLICT`, a changed receipt, or any other response is corruption and must not produce local release completion. The server retains a receipt tombstone after reclaiming the blob, so release is idempotent across process crashes. Release can never run before the complete result and local acknowledgement are durable. It is storage cleanup, not permission for a dependent side effect, and it never causes the completed tool call to be reacquired or redispatched. Recovery therefore drives every dependency-ready business operation as far as remote visibility allows before entering a separate cleanup pass; no result-release poll is allowed to head-of-line block business work that was ready at the start of that pass.

Generation rollover is a durability handshake. A claim begins at generation 1. `PENDING` may advance at a higher revision to `COMMITTED` or `ABORTED`. While the caller's `after_revision` is below an `ABORTED` revision, acquisition returns that abandonment proof. Only an acquisition whose `after_revision` includes the proof may atomically replace it with `READY` generation N+1, a fresh token, and a higher revision. Thus a crash before journaling `ABORTED` cannot prematurely rotate authority, while a restart or compaction retaining it can make progress. Replicas can still answer below `after_revision`; those stale responses are ignored before inspecting their stale fingerprint, token, generation, receipt, or state. A non-stale generation change without the durable predecessor abandonment, a skipped generation, token drift within a generation, `READY` after `PENDING` in the same generation, or any authority after `ABORTED` in the same generation is corruption. Control-plane acquisitions, result reads, and result releases use independent transport request IDs so response caching cannot preserve a stale state across polls or restarts.

The gateway first appends and fsyncs `PREPARED`, then calls `acquire_call`. It appends and fsyncs `DISPATCHED` with the same snapshot and fingerprint plus the acquired token, generation, and revision before invoking a side-effecting tool. It sends the snapshotted name and arguments plus the token as `io.klavis/dispatchToken` and the integer generation as `io.klavis/dispatchGeneration` metadata. A crash after acquisition but before `DISPATCHED` is safe because `PREPARED` retains the exact key and fingerprint needed to reacquire the same durable generation and token without consulting changed migration code. A crash after `DISPATCHED` but before server acceptance is safe because `READY` returns them again. Once that side-effect request returns, confirmation uses fresh acquisitions and does not invoke the endpoint again merely because a lagging replica still reports `READY` for the just-sent generation. It waits for authoritative progress, or dispatches only a genuinely new fenced successor obtained after durable abandonment. After rollover, the server rejects delayed calls carrying the predecessor token or generation. The server therefore never executes two effects for one durable claim, and no transport response can inject an unauthenticated result into later bindings.

Recovery completes a `RESULT_DURABLE` operation locally without another acquisition or side-effecting tool call: it writes `ACKED`, retains any receipt for the later cleanup pass, and does not reacquire or redispatch that operation. Other incomplete valid operations are retried when all declared dependencies have reached a durable successful result. Cyclic, missing, or failed dependencies are invalid input rather than permission to reorder calls.

Persisted arguments may bind values from a prior result using `{"$result":{"operation_id":"allocate","path":["worker_ids",0]}}`. Bindings can appear recursively inside argument objects or arrays. The referenced operation is scoped to the same session and must be a declared transitive dependency. `path` traverses object keys and nonnegative array indexes in order. Recovery resolves bindings from the durable result recorded in the journal; it must not redispatch a completed producer merely to reconstruct its output. Invalid references are rejected rather than sent to the tool server.

Only one execution or recovery invocation may own a journal at a time. For `recover`, the ownership interval begins before loading recovery state and ends after the final lifecycle or release record is durable. For `execute`, ownership begins before inspecting or repairing the existing journal, includes every new `PLANNED` append, and continues through recovery and result release. This prevents a new plan from being appended behind a torn tail or interleaved with another owner's lifecycle. Concurrent invocations for the same journal wait for that owner, then reconstruct the new state; they must not emit duplicate `DISPATCHED`, `RESULT_DURABLE`, `ACKED`, or `RESULT_RELEASED` records for work completed by the first owner. Ownership is automatically released if its process crashes so a waiter can safely retry an uncertain dispatch or idempotent cleanup. Journals at different paths remain independent.

Production journals may contain thousands of operations and dependency chains deeper than the Python recursion limit. Validation and scheduling must be stack-safe and linear in the operation/dependency graph apart from the actual traversal needed for result bindings. A complete 4,096-operation chain is a supported journal, not corrupt input.

The `compact` command replaces the durable history with a normalized checkpoint at `<journal>.checkpoint`. Newly written checkpoints use `format_version: 2`. They contain the byte length and SHA-256 digest of the journal bytes they cover, a normalized `state` object, the SHA-256 digest of that state's canonical compact JSON encoding, and a content-addressed `checkpoint_id`. The ID is the lowercase SHA-256 digest of canonical compact JSON for `{"covered_length":N,"covered_sha256":"...","state_sha256":"..."}` (sorted keys, separators `,` and `:`, UTF-8, non-ASCII unescaped). The state contains an ordered `operations` array; each entry retains the complete operation, its latest lifecycle `status`, its nonnegative dispatch-attempt count, and any dispatch key, wire snapshot, fingerprint, current generation, remote revision, receipt, release status, or durable result required by that status. A `PREPARED` entry has zero attempts and retains only its complete prepared identity; an `ACKED` entry with a receipt is pending cleanup; `RESULT_RELEASED` requires the same receipt and is final. Format-1 checkpoints remain readable for migration.

Compaction runs under the same journal ownership as recovery. It writes and fsyncs `<journal>.checkpoint.tmp`, atomically replaces the active checkpoint, and durably publishes that rename. It then writes and fsyncs a replacement journal containing exactly `{"event":"CHECKPOINT_BASE","checkpoint_id":"..."}`, atomically replaces the old journal, and durably publishes that rename. A crash between those replacements can leave the newly published checkpoint beside its old covered bytes; recovery verifies the prefix digest and skips exactly those bytes. After journal rebasing, recovery consumes the matching base marker before applying suffix records. This provenance marker lets a suffix grow beyond the old prefix length without ambiguity and makes a mismatched, rolled-back, or misplaced checkpoint/journal pair corruption instead of silently merging unrelated histories. For a format-2 checkpoint with `covered_length: 0`, only an actually empty journal is the pre-rebase state; any non-empty journal must begin with the matching base marker, because accepting a vacuous empty prefix would adopt unrelated history. A base marker with the wrong checkpoint ID, or a format-2 checkpoint whose ID does not authenticate its coverage and state digests, is rejected before lifecycle processing. Incomplete temporary files are ignored. Format-1 checkpoints retain their legacy loading behavior and are upgraded on the next compaction. Compaction preserves terminal results for future bindings, pending result release after `ACKED`, every zero-attempt `PREPARED` identity, and the current token, generation, remote-revision high-watermark, commit receipt, and latest durable pending, aborted, or committed observation of every uncertain fenced attempt so acquisition remains safe and live even after migration code changes or the server offloads an inline result.
